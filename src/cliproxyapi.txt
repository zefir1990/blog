Title: CLIProxyAPI
Slug: cliproxyapi
Categories: notes
CLIProxyAPI — это локальный сервер, который превращает CLI-подписки и OAuth-аккаунты в обычный HTTP API, совместимый с OpenAI, Gemini и Claude. Идея простая: у вас может быть несколько аккаунтов Codex, Claude Code, Gemini CLI, Antigravity, Kimi или Grok Build, а приложения и библиотеки умеют разговаривать только с привычными API. CLIProxyAPI стоит между ними, принимает запрос в одном формате, переводит его в нужный формат провайдера и отдаёт ответ обратно.

Проект написан на Go, распространяется под лицензией MIT и поставляется одной бинарной программой без зависимостей. Авторизация выполняется через OAuth прямо из командной строки, токены сохраняются в каталоге `~/.cli-proxy-api`, поэтому повторный вход нужен только после истечения или отзыва доступа.

Основные возможности:

- эндпоинты Chat Completions, Responses, Claude Messages и Gemini API;
- потоковые и обычные ответы, вызов функций, изображения на входе;
- несколько аккаунтов одного провайдера с балансировкой по кругу;
- автоматическое переключение на другой аккаунт при ошибке или исчерпании квоты;
- собственные API-ключи для клиентов, отдельно от учётных данных провайдеров;
- подключение сторонних OpenAI-совместимых сервисов через конфигурацию;
- панель управления и Management API для правки настроек без перезапуска;
- Go SDK для встраивания прокси в свои приложения.

Поддерживаются Gemini (включая Antigravity и Gemini CLI), OpenAI Codex, Claude Code, xAI Grok, Kimi, GitHub Copilot, Devin и Meta Muse. Модель можно указать алиасом, а разные аккаунты можно пометить приоритетом, весом или префиксом, чтобы направлять запросы на конкретный пул.

Установка сводится к скачиванию архива со страницы релизов, распаковке и запуску бинарника. Внутри архива уже лежит `config.example.yaml`, который нужно скопировать в `config.yaml` и отредактировать. Минимальной конфигурации достаточно, чтобы сервер поднялся на порту 8317 и принимал запросы с локальным ключом:

<pre><code>
config-version: 8

server:
  host: "127.0.0.1"
  port: 8317

management:
  secret-key: "change-me"

access:
  api-keys:
    - "local-dev-key"
</code></pre>

Затем выполняется вход в нужные аккаунты. Каждый провайдер имеет свой флаг, а браузер открывается автоматически:

<pre><code>
cli-proxy-api --codex-login
cli-proxy-api --claude-login
cli-proxy-api --antigravity-login
cli-proxy-api --kimi-login
cli-proxy-api --xai-login
cli-proxy-api --copilot-login
</code></pre>

После входа сервер запускается обычным вызовом без флагов и слушает `http://127.0.0.1:8317`. Список доступных моделей можно получить запросом к `/v1/models`. Проверка через обычный HTTP-клиент выглядит так:

<pre><code>
curl http://127.0.0.1:8317/v1/chat/completions \
  -H "Authorization: Bearer local-dev-key" \
  -H "Content-Type: application/json" \
  -d "{\"model\":\"gpt-6.1-sol\",\"messages\":[{\"role\":\"user\",\"content\":\"Привет\"}]}"
</code></pre>

Самый интересный сценарий — подключить к прокси существующие инструменты. Claude Code достаточно направить на локальный адрес:

<pre><code>
export ANTHROPIC_BASE_URL=http://127.0.0.1:8317
export ANTHROPIC_AUTH_TOKEN=local-dev-key
claude
</code></pre>

В Windows вместо `export` используется `set`, синтаксис остальных переменных тот же.

Любой клиент OpenAI, включая официальный Python SDK, тоже работает без изменений в коде, если поменять базовый адрес:

<pre><code>
from openai import OpenAI

client = OpenAI(
    base_url="http://127.0.0.1:8317/v1",
    api_key="local-dev-key",
)

response = client.chat.completions.create(
    model="gpt-6.1-sol",
    messages=[{"role": "user", "content": "Привет"}],
)

print(response.choices[0].message.content)
</code></pre>

Для OpenCode прокси подключается как собственный OpenAI-совместимый провайдер. Достаточно описать его в глобальном или проектном `opencode.json` и передать локальный ключ через переменную окружения:

<pre><code>
{
  "$schema": "https://opencode.ai/config.json",
  "providers": {
    "cliproxyapi": {
      "name": "CLIProxyAPI",
      "env": ["CLIPROXYAPI_KEY"],
      "package": "@opencode/ai/providers/openai-compatible",
      "settings": {
        "baseURL": "http://127.0.0.1:8317/v1"
      },
      "models": {
        "gpt-6.1-sol": {
          "name": "GPT-6.1 Sol"
        }
      }
    }
  }
}
</code></pre>

<pre><code>
export CLIPROXYAPI_KEY=local-dev-key
opencode
</code></pre>

После запуска модель выбирается через `/models`, а по умолчанию её можно закрепить строкой `"model": "cliproxyapi/gpt-6.1-sol"`. Имена моделей берутся из ответа `/v1/models` и перечисляются в `models` вручную, потому что для собственного провайдера OpenCode не подгружает каталог автоматически. Для моделей Claude, идущих через OpenAI-совместимый маршрут, стоит добавить `"compatibility": { "cacheFormat": "anthropic" }`, иначе OpenCode не расставит точки кэширования промпта. Конфигурация подхватывается без перезапуска, поэтому новый аккаунт или модель в прокси появляются в OpenCode сразу после сохранения файла.

Для Gemini-клиентов используется `/v1beta`, для Anthropic-совместимых — `/v1/messages`. Прокси сам решает, какой транспорт и какой аккаунт выбрать, и умеет держать сессию на одном аккаунте, чтобы не терять кэш промптов.

При нескольких подписках балансировка по умолчанию идёт по кругу. В конфигурации можно включить взвешенное распределение, режим заполнения первого аккаунта, привязку сессий, повторы на других учётных данных и задержки остывания после ошибок. Для наблюдения за состоянием есть Management API и встроенная веб-панель, а в конфигурации задаётся ключ доступа к ним.

Проект активно развивается: на момент публикации у репозитория более 59 тысяч звёзд, вокруг него выросла целая экосистема графических оболочек и панелей для macOS, Windows и Linux. Есть отдельный десктопный клиент EasyCLIProxyAPI, который даёт графический интерфейс настройки и значок в системном трее. Для тех, кто хочет встроить прокси в собственное приложение, предусмотрен Go SDK с поддержкой собственных исполнителей и трансляторов протоколов.

Отдельно стоит сказать о рисках. Использование OAuth-доступа вне официального клиента может нарушать условия обслуживания провайдеров, а аккаунты могут попадать под ограничения. Прокси имеет смысл запускать только со своими учётными данными, привязывать к `127.0.0.1` и закрывать ключом, если доступ к нему открывается по сети. Это инструмент для удобного объединения собственных подписок, а не способ обхода оплаты.
