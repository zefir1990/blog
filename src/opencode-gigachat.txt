Title: Как подключить GigaChat к OpenCode
Slug: opencode-gigachat
Categories: notes
OpenCode — открытый агент для программирования, который работает прямо в терминале: читает файлы проекта, правит код, запускает команды и тесты, ищет по репозиторию и работает с git. Его сильная сторона в том, что он не привязан к одному поставщику моделей и умеет подключать десятки провайдеров.

GigaChat — большая языковая модель от Сбера. В готовом списке провайдеров OpenCode её нет, но это не проблема: OpenCode подключает произвольных провайдеров через пакеты Vercel AI SDK. Для GigaChat есть пакет <b>gigachat-ai-sdk-provider</b>, который берёт на себя авторизацию по OAuth и обновление токена доступа. Отдельный нюанс — сертификаты Минцифры: без них Node не доверяет серверам GigaChat, и запросы падают с ошибкой проверки сертификата.

В этой заметке я опишу, как получить ключ, поставить сертификаты и подключить GigaChat к OpenCode.

<h2>Что понадобится</h2>

Для работы нужны три вещи:

<ul>
<li><b>Установленный OpenCode.</b> Если агент ещё не стоит, порядок установки я разбирал в отдельной заметке про OpenCode и DeepSeek.</li>
<li><b>Аккаунт GigaChat.</b> Регистрация в GigaChat Studio и ключ авторизации — для входа понадобится Sber ID.</li>
<li><b>Современный терминал.</b> Подойдёт WezTerm, Alacritty, Ghostty, Kitty или любой другой.</li>
</ul>

<h2>Ключ авторизации GigaChat</h2>

Ключ создаётся в личном кабинете GigaChat Studio. Заходим на developers.sber.ru/studio, авторизуемся и создаём проект в разделе <b>GigaChat API</b>. В настройках проекта есть блок с авторизационными данными: строка, которую оттуда копируют, — это уже готовый ключ авторизации в base64. Именно он подставляется в переменную окружения, а не пара клиент-секрет по отдельности.

Вместе с ключом задаётся <b>scope</b> — область доступа:

<ul>
<li><b>GIGACHAT_API_PERS</b> — для физических лиц.</li>
<li><b>GIGACHAT_API_B2B</b> — для ИП и юридических лиц.</li>
<li><b>GIGACHAT_API_CORP</b> — корпоративный доступ.</li>
</ul>

Показанное значение ключа стоит сразу сохранить: позже повторно его не показывают, а при необходимости придётся выпускать новый.

Важно понимать, что это за строка. Ключ авторизации — это не отдельный секрет, а уже закодированная в base64 пара <b>client_id:client_secret</b>. Библиотека gigachat-js подставляет его в OAuth-запрос заголовком:

<pre><code>
Authorization: Basic ваш_ключ_авторизации
</code></pre>

В ответ приходит JWE-токен доступа со сроком жизни около получаса, и дальше библиотека обновляет его автоматически. Пакет сам проверяет, что значение похоже на base64, и предупреждает, если в переменную случайно попал «сырой» client secret. Поэтому в конфиг и переменную окружения нужно передавать именно готовую base64-строку из кабинета, а не пару client_id и client_secret по отдельности.

<h2>Сертификаты Минцифры</h2>

GigaChat API использует сертификаты НУЦ Минцифры. В стандартном хранилище доверенных корней их нет, поэтому при попытке получить токен доступа запрос завершается ошибкой вида:

<pre><code>
self-signed certificate in certificate chain
</code></pre>

Сертификаты можно поставить на уровне операционной системы — тогда им будут доверять браузер и системные утилиты. Но OpenCode работает на Node и Bun, поэтому надёжнее и проще указать файл сертификата прямо в переменной <b>NODE_EXTRA_CA_CERTS</b>. Скачаем корневой и выпускающий сертификаты и сложим их в один PEM-файл:

<pre><code>
curl -s https://gu-st.ru/content/lending/russian_trusted_root_ca_pem.crt -o russian_trusted_root_ca_pem.crt
curl -s https://gu-st.ru/content/lending/russian_trusted_sub_ca_pem.crt -o russian_trusted_sub_ca_pem.crt
cat russian_trusted_root_ca_pem.crt russian_trusted_sub_ca_pem.crt > russian_trusted_ca_bundle.pem
</code></pre>

Файл можно положить в удобное место и указывать его полный путь при запуске агента. Обратите внимание: у скачанных файлов расширение .crt, но содержимое — обычный PEM, дополнительная конвертация не нужна.

<h2>Подключение к OpenCode</h2>

Провайдер описывается в конфигурационном файле <b>opencode.json</b>. OpenCode сам скачает и подключит npm-пакет, указанный в поле <b>npm</b>, найдёт в нём фабрику <b>createGigaChat</b> и передаст ей опции. Достаточно перечислить модели по их идентификаторам из API.

Файл можно разместить в двух местах:

<ul>
<li><b>Глобально</b> — ~/.config/opencode/opencode.json. Настройки действуют для всех проектов пользователя.</li>
<li><b>В проекте</b> — opencode.json в корне проекта. Такой конфиг имеет больший приоритет и его безопасно коммитить в git.</li>
</ul>

Оба файла используют одну схему и объединяются: проектный перекрывает глобальный только по совпадающим ключам, остальные настройки сохраняются. Поддерживается и расширение .jsonc. Если GigaChat нужен лишь в части репозиториев, удобнее держать провайдера в проектном конфиге, а не в глобальном.

<pre><code>
{
  "$schema": "https://opencode.ai/config.json",
  "provider": {
    "gigachat": {
      "npm": "gigachat-ai-sdk-provider",
      "name": "GigaChat",
      "models": {
        "GigaChat-2-Max": { "name": "GigaChat 2 Max" },
        "GigaChat-2-Pro": { "name": "GigaChat 2 Pro" },
        "GigaChat-2": { "name": "GigaChat 2 Lite" },
        "GigaChat": { "name": "GigaChat" }
      }
    }
  }
}
</code></pre>

Здесь перечислены модели, доступные персональному ключу. Если у вас проект для ИП или юрлица с доступом к GigaChat 3, добавьте в блок models нужные идентификаторы из метода models.

Сам ключ удобнее не хранить в файле, а передавать переменной окружения: пакет gigachat-js читает её автоматически. Значение scope тоже можно задать переменной. Осталось выставить путь к сертификатам и запустить агент:

<pre><code>
export GIGACHAT_CREDENTIALS=ваш_ключ_авторизации
export GIGACHAT_SCOPE=GIGACHAT_API_PERS
export NODE_EXTRA_CA_CERTS=/путь/к/russian_trusted_ca_bundle.pem
opencode
</code></pre>

Такой вариант хорош ещё и тем, что секрет не оседает в локальном хранилище auth.json: он живёт только в окружении процесса. Для CI и одноразовых запусков это удобнее.

<h2>Модели</h2>

Набор доступных моделей зависит от scope ключа. Персональному ключу (GIGACHAT_API_PERS) доступно семейство GigaChat и GigaChat 2:

<ul>
<li><b>GigaChat</b> — базовая модель.</li>
<li><b>GigaChat-2</b> — быстрая и лёгкая модель для повседневных задач, в интерфейсе отображается как Lite.</li>
<li><b>GigaChat-2-Pro</b> — усовершенствованная модель для ресурсоёмких задач.</li>
<li><b>GigaChat-2-Max</b> — самая мощная из доступных по персональному ключу.</li>
</ul>

Семейство GigaChat 3 (GigaChat-3-Ultra, GigaChat-3-Pro, открытые модели вроде GigaChat3.5-432B-A28B-Reasoning) видно в каталоге консоли, но персональному ключу оно недоступно: для него нужен проект ИП или юрлица со scope GIGACHAT_API_B2B или GIGACHAT_API_CORP и подходящим тарифом. На персональном ключе такая модель отвечает ошибкой:

<pre><code>
{"status":404,"message":"No such model"}
</code></pre>

Проверить, что в реальности отдаёт ваш ключ, можно запросом к списку моделей:

<pre><code>
curl -H "Authorization: Bearer <токен_доступа>" https://gigachat.devices.sberbank.ru/api/v1/models
</code></pre>

Ещё два нюанса. Идентификаторы моделей в API не совпадают с отображаемыми названиями — лёгкая модель вызывается как <b>GigaChat-2</b>, а не GigaChat-2-Lite. И каталог в консоли показывает не то же самое, что доступно вашему ключу, поэтому ориентироваться стоит на ответ метода models, а не на список с ценами.

В интерфейсе список моделей открывается командой:

<pre><code>
/models
</code></pre>

Для рутины в репозитории — навигации по файлам, мелких правок, запуска тестов — вполне хватает GigaChat-2. На сложные задачи и проектирование имеет смысл переключаться на Pro или Max.

<h2>Первый запуск в проекте</h2>

Переходим в каталог проекта и запускаем агента:

<pre><code>
cd ваш_проект
opencode
</code></pre>

Первым делом полезно инициализировать агент:

<pre><code>
/init
</code></pre>

OpenCode проанализирует структуру проекта и создаст файл <b>AGENTS.md</b> — инструкции для агента. Этот файл стоит закоммитить в git: он помогает агенту понимать принятые в проекте соглашения и паттерны.

<h2>Альтернатива: локальный прокси</h2>

Если по каким-то причинам не хочется тянуть npm-провайдер, тот же результат даёт локальный прокси. У команды GigaChat есть официальный <b>gpt2giga</b> — FastAPI-сервис, который транслирует запросы в формате OpenAI, Anthropic и Gemini в GigaChat API и сам обновляет токен доступа. Он поднимается локально на порту 8090, после чего в OpenCode настраивается обычный OpenAI-совместимый провайдер через пакет <b>@ai-sdk/openai-compatible</b> с базовым адресом http://localhost:8090/v1. Минус этого пути в том, что рядом с OpenCode нужно держать ещё и запущенный Python-сервис.

<pre><code>
{
  "$schema": "https://opencode.ai/config.json",
  "provider": {
    "gigachat": {
      "npm": "@ai-sdk/openai-compatible",
      "name": "GigaChat (proxy)",
      "options": {
        "baseURL": "http://localhost:8090/v1"
      },
      "models": {
        "GigaChat-2-Max": { "name": "GigaChat 2 Max" }
      }
    }
  }
}
</code></pre>

<h2>На что обратить внимание</h2>

Пара практических моментов, которые чаще всего мешают при первой настройке:

<ul>
<li><b>Ошибка проверки сертификата.</b> Сообщение про self-signed certificate в цепочке означает, что переменная NODE_EXTRA_CA_CERTS не подхватилась: проверьте путь к PEM-файлу и то, что агент запущен в том же окружении.</li>
<li><b>Ошибка 401.</b> Как правило, это неверный ключ авторизации или несовпадающий scope — для физлица нужен GIGACHAT_API_PERS.</li>
<li><b>Ошибка 404 с текстом No such model.</b> Это не сбой подключения, а отсутствие доступа к конкретной модели. Уберите её из конфига или замените на доступную. В сообщении вида GigaChat 404: Unknown error виноват тот же ответ GigaChat — провайдер просто не смог разобрать тело ошибки.</li>
<li><b>Cost.</b> OpenCode не требует подписки: вы платите GigaChat напрямую по факту расхода токенов, поэтому длинные сессии предсказуемы по цене.</li>
<li><b>Качество модели.</b> На сложных архитектурных задачах модели разных классов отличаются, поэтому для проектирования имеет смысл брать модель посильнее, а рутину отдавать быстрой.</li>
</ul>
