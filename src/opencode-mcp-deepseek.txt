Title: MCP в OpenCode на DeepSeek: как подключить внешние инструменты
Slug: opencode-mcp-deepseek
Categories: notes
MCP (Model Context Protocol) — открытый протокол, который описывает, как подключать к языковой модели внешние инструменты и источники данных: файловую систему, документацию, трекер задач, баг-трекер или собственный сервис. Вместо того чтобы встраивать каждый инструмент в агента, вы поднимаете отдельный MCP-сервер, а агент общается с ним по стандартной схеме.

OpenCode поддерживает MCP из коробки: и локальные серверы, которые запускаются дочерним процессом, и удалённые, доступные по HTTP. Важный момент — весь MCP-слой реализован на стороне самого OpenCode, а не на стороне провайдера модели. Поэтому DeepSeek получает инструменты MCP как обычные функции в запросе, и ему не нужно ничего знать про сам протокол.

В этой заметке я разберу, как добавить локальный и удалённый сервер, как пройти авторизацию, как не утонуть в токенах и что учитывать при работе с моделями DeepSeek.

<h2>Что понадобится</h2>

Для работы нужны три вещи:

<ul>
<li><b>Установленный OpenCode.</b> Если агент ещё не настроен, порядок установки и подключения DeepSeek я разбирал в отдельной заметке.</li>
<li><b>Node.js и npx.</b> Нужны для локальных MCP-серверов, которые распространяются как npm-пакеты.</li>
<li><b>Ключи доступа.</b> Только для тех удалённых серверов, которые требуют авторизации. Публичные серверы вроде Context7 работают и без ключа, но с меньшими лимитами.</li>
</ul>

<h2>Как это устроено</h2>

Серверы описываются в конфигурации OpenCode в блоке <b>mcp</b>. У каждого сервера есть уникальное имя, по которому его можно упомянуть в запросе. Инструменты сервера регистрируются с префиксом этого имени, поэтому конфликтов между разными серверами не возникает.

После подключения инструменты MCP становятся доступны модели наравне со встроенными: чтением файлов, правкой кода и запуском команд. С точки зрения DeepSeek это обычные функции, которые агент может вызвать, — именно поэтому связка работает без какой-либо поддержки MCP на стороне API модели.

<h2>Локальный сервер</h2>

Самый простой способ познакомиться с механизмом — тестовый сервер <b>@modelcontextprotocol/server-everything</b>. Добавим его в файл <b>opencode.json</b> в корне проекта:

<pre><code>
{
  "$schema": "https://opencode.ai/config.json",
  "mcp": {
    "mcp_everything": {
      "type": "local",
      "command": ["npx", "-y", "@modelcontextprotocol/server-everything"]
    }
  }
}
</code></pre>

Поле <b>command</b> — это команда запуска сервера и её аргументы в виде массива. После перезапуска OpenCode инструменты появятся в сессии, и их можно попросить явно:

<pre><code>
используй инструмент mcp_everything, чтобы сложить 3 и 4
</code></pre>

У локального сервера есть ещё несколько полезных полей. <b>environment</b> задаёт переменные окружения процесса, <b>cwd</b> — рабочую директорию, <b>timeout</b> — таймаут запросов в миллисекундах, а <b>enabled</b> позволяет временно отключить сервер, не удаляя его из конфигурации.

<h2>Удалённый сервер</h2>

Удалённые серверы удобнее: не нужно ничего запускать локально, а доступ к ним идёт по URL. Хороший пример — Context7, который ищет актуальную документацию библиотек. Он подключается без ключа:

<pre><code>
{
  "$schema": "https://opencode.ai/config.json",
  "mcp": {
    "context7": {
      "type": "remote",
      "url": "https://mcp.context7.com/mcp"
    }
  }
}
</code></pre>

Если у вас есть бесплатный аккаунт Context7, ключ поднимает лимиты. Заголовки передаются через блок <b>headers</b>, а сам ключ удобно держать в переменной окружения:

<pre><code>
{
  "$schema": "https://opencode.ai/config.json",
  "mcp": {
    "context7": {
      "type": "remote",
      "url": "https://mcp.context7.com/mcp",
      "headers": {
        "CONTEXT7_API_KEY": "{env:CONTEXT7_API_KEY}"
      }
    }
  }
}
</code></pre>

Конструкция <b>{env:ИМЯ}</b> подставляет значение переменной окружения при загрузке конфигурации, поэтому ключ не попадает в репозиторий. Перед запуском агента переменную нужно экспортировать в терминале.

Ещё один полезный публичный сервер — Grep by Vercel, поиск по примерам кода на GitHub:

<pre><code>
{
  "$schema": "https://opencode.ai/config.json",
  "mcp": {
    "gh_grep": {
      "type": "remote",
      "url": "https://mcp.grep.app"
    }
  }
}
</code></pre>

<h2>Авторизация через OAuth</h2>

Часть удалённых серверов требует OAuth. OpenCode умеет проходить этот сценарий сам: он замечает ответ 401, запускает авторизацию и сохраняет токены. Для Sentry достаточно указать сервер:

<pre><code>
{
  "$schema": "https://opencode.ai/config.json",
  "mcp": {
    "sentry": {
      "type": "remote",
      "url": "https://mcp.sentry.dev/mcp",
      "oauth": {}
    }
  }
}
</code></pre>

После этого авторизацию можно запустить вручную — откроется браузер:

<pre><code>
opencode mcp auth sentry
</code></pre>

Служебные команды полезны и в повседневной работе. <b>opencode mcp list</b> показывает серверы и статус авторизации, <b>opencode mcp logout</b> удаляет сохранённые токены, а <b>opencode mcp debug</b> проверяет сетевое подключение и OAuth-обнаружение для конкретного сервера. Токены хранятся локально в файле <b>~/.local/share/opencode/mcp-auth.json</b>.

Если сервер использует не OAuth, а обычный API-ключ, автоматическую авторизацию стоит отключить, иначе OpenCode будет пытаться пройти OAuth там, где это не нужно:

<pre><code>
{
  "$schema": "https://opencode.ai/config.json",
  "mcp": {
    "my-api-key-server": {
      "type": "remote",
      "url": "https://mcp.example.com/mcp",
      "oauth": false,
      "headers": {
        "Authorization": "Bearer {env:MY_API_KEY}"
      }
    }
  }
}
</code></pre>

<h2>Управление инструментами</h2>

Инструменты MCP расходуют контекст: каждый сервер добавляет в запрос описания своих функций. Поэтому серверы, которые нужны редко, лучше держать выключенными. Сделать это можно глобально через блок <b>tools</b>:

<pre><code>
{
  "$schema": "https://opencode.ai/config.json",
  "mcp": {
    "my-mcp-foo": {
      "type": "local",
      "command": ["npx", "-y", "my-mcp-command-foo"]
    },
    "my-mcp-bar": {
      "type": "local",
      "command": ["npx", "-y", "my-mcp-command-bar"]
    }
  },
  "tools": {
    "my-mcp*": false
  }
}
</code></pre>

Шаблон <b>my-mcp*</b> отключает все инструменты, имя которых начинается с этого префикса. Если серверов много, разумнее выключить их глобально и включать точечно для конкретного агента:

<pre><code>
{
  "$schema": "https://opencode.ai/config.json",
  "mcp": {
    "my-mcp": {
      "type": "local",
      "command": ["npx", "-y", "my-mcp-command"],
      "enabled": true
    }
  },
  "tools": {
    "my-mcp*": false
  },
  "agent": {
    "my-agent": {
      "tools": {
        "my-mcp*": true
      }
    }
  }
}
</code></pre>

<h2>Особенности DeepSeek</h2>

Связка с DeepSeek работает потому, что модели поддерживают вызов функций, а MCP-инструменты для них выглядят как самые обычные функции. Сам DeepSeek при этом не подключает MCP-серверы и не должен: подключением занимается OpenCode.

На что стоит обратить внимание:

<ul>
<li><b>Выбор модели.</b> Для рутины и небольших правок достаточно <b>deepseek-flash</b>. Задачи, где нужно удержать в голове много контекста и аккуратно выбрать инструмент, лучше отдавать <b>deepseek-v4-pro</b>.</li>
<li><b>Размер контекста.</b> Тяжёлые серверы вроде GitHub MCP добавляют очень много токенов и вместе с большим проектом легко упираются в лимит. Включайте их только на время конкретной задачи.</li>
<li><b>Стоимость.</b> Схемы инструментов отправляются в каждом запросе, поэтому чем больше серверов включено, тем дороже каждая итерация. Платите вы провайдеру напрямую, так что лишние серверы заметны по счёту.</li>
<li><b>Подсказки агенту.</b> Надёжнее не полагаться на догадливость модели, а прямо называть сервер в запросе или прописать правило в <b>AGENTS.md</b>.</li>
</ul>

Пример правила для <b>AGENTS.md</b>, чтобы агент сам обращался к нужному источнику:

<pre><code>
Когда нужно посмотреть документацию библиотеки, используй инструменты context7.
</code></pre>

<h2>Практический рецепт</h2>

Для повседневной работы обычно хватает двух серверов: Context7 для документации и одного узкого сервера под конкретную задачу — например, Sentry для разбора ошибок или Grep для поиска примеров кода. Остальные лучше держать выключенными и включать по мере необходимости.

Мой порядок действий такой: добавляю сервер в <b>opencode.json</b>, перезапускаю OpenCode, проверяю список через <b>opencode mcp list</b>, затем задаю пробный вопрос с явным упоминанием сервера. Если инструмент не вызывается, смотрю в сторону <b>opencode mcp debug</b> и таймаута — медленный сервер может не успевать ответить за отведённые 30 секунд.

<h2>На что обратить внимание</h2>

Пара практических моментов. MCP-серверы — это доверенный код: локальный сервер запускается на вашей машине с вашими правами, а удалённому вы отправляете данные запроса. Поэтому ставить случайные серверы из интернета стоит с той же осторожностью, что и любой сторонний CLI.

Ключи и токены держите в переменных окружения и не коммитьте в репозиторий. OAuth-токены OpenCode хранит локально, но на общей машине это тоже стоит учитывать: <b>opencode mcp logout</b> удаляет их, когда доступ больше не нужен.

И ещё: не включайте всё сразу. MCP добавляет инструменты в контекст, а контекст — это деньги и качество ответа. Два-три действительно нужных сервера работают заметно лучше, чем десять подключённых на всякий случай.
