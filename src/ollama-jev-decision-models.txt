Title: Jev-модели решений в Ollama: практическое использование /v1/systemone
Slug: ollama-jev-decision-models
Categories: notes
Начиная с версии 0.35 Ollama поддерживает decision-модели, построенные на Jev API от TypeSafe. Это не чат-модели в привычном смысле: они не пишут текст, а отвечают на набор типизированных вопросов о переданном состоянии. Для классификации, маршрутизации, модерации и триажа это оказывается быстрее и надёжнее, чем просить обычную LLM вернуть JSON и потом разбирать её ответ.

В этой заметке я разберу, что такое decision-модели, как они устроены на уровне HTTP, какие модели уже доступны, и как встроить их в существующий код так, чтобы обычные генеративные модели продолжали работать.

<h2>Чем decision-модели отличаются от обычных</h2>

Обычная LLM получает промпт и генерирует текст токен за токеном. Даже если попросить её ответить одним словом, внутри всё равно происходит генерация, а формат ответа приходится контролировать схемой, инструкциями и последующей проверкой. Decision-модель устроена иначе: вы передаёте состояние и вопросы с типами, а модель возвращает вероятности и выбранные варианты. Никакого свободного текста, никакого парсинга JSON из ответа.

Новый endpoint называется /v1/systemone. В одном запросе можно задать сразу несколько вопросов, и модель ответит на все. Это удобно для задач, где нужно принять несколько связанных решений: например, определить команду, необходимость возврата и срочность тикета.

<h2>Какие модели доступны</h2>

Сейчас через Ollama можно запустить три decision-модели:

<ul>
<li><b>nimble</b> — открытая модель на 9 миллиардов параметров от Bespoke Labs. Это самая крупная и самая точная из доступных.</li>
<li><b>tev1</b> — экспериментальная модель на 4 миллиарда параметров от Together AI.</li>
<li><b>tev1:0.8b</b> — экспериментальная модель на 0.8 миллиарда параметров от Together AI. Самая быстрая и самая лёгкая.</li>
</ul>

Все они работают локально, не требуют оплаты и не отправляют данные во внешний сервис. Поддерживаются Ollama 0.35 и новее.

<h2>Установка</h2>

Сначала проверьте версию Ollama:

<pre><code>
ollama --version
</code></pre>

Затем загрузите нужную модель. Для самой лёгкой:

<pre><code>
ollama pull tev1:0.8b
</code></pre>

Для полной версии tev1:

<pre><code>
ollama pull tev1
</code></pre>

Для nimble:

<pre><code>
ollama pull nimble
</code></pre>

Модель nimble занимает около 9.5 ГБ на диске, поэтому перед загрузкой стоит освободить место. tev1:0.8b занимает меньше гигабайта.

<h2>Первый запрос через curl</h2>

Простейший пример — определить, является ли текст объявлением о вакансии:

<pre><code>
curl http://localhost:11434/v1/systemone -d '{
  "model": "tev1:0.8b",
  "state": {
    "message": "Senior Swift developer, Berlin, remote friendly"
  },
  "questions": {
    "isJob": {
      "type": "noul",
      "instructions": "Does the message advertise a job posting that someone can apply to?"
    }
  }
}'
</code></pre>

Ответ выглядит так:

<pre><code>
{
  "model": "tev1:0.8b",
  "answers": {
    "isJob": {
      "type": "noul",
      "noul": 0.921
    }
  },
  "usage": {
    "input_tokens": 42,
    "output_tokens": 0
  }
}
</code></pre>

Поле noul — это вероятность от 0 до 1. Решение принимается сравнением с порогом, обычно 0.5. В отличие от генеративной модели, здесь не нужно просить ответ в формате JSON и потом проверять, что модель его не сломала.

<h2>Типы вопросов</h2>

Decision-модели поддерживают три типа вопросов.

<b>noul</b> — бинарный вопрос. Возвращает вероятность того, что утверждение истинно:

<pre><code>
{
  "questions": {
    "refund": {
      "type": "noul",
      "instructions": "Does the customer explicitly ask for a refund?"
    }
  }
}
</code></pre>

<b>choice</b> — выбор одного варианта из заданного набора. Возвращает выбранный вариант, вероятности всех вариантов и confidence:

<pre><code>
{
  "questions": {
    "team": {
      "type": "choice",
      "instructions": "Which team should handle this ticket?",
      "criteria": {
        "billing": "Payments and refunds",
        "technical": "Bugs and integrations",
        "other": "None of the above"
      }
    }
  }
}
</code></pre>

<b>score</b> — оценка по шкале. Возвращает число, легенду и вероятности для каждой точки шкалы:

<pre><code>
{
  "questions": {
    "urgency": {
      "type": "score",
      "instructions": "How urgent is this ticket?",
      "criteria": ["Routine", "Soon", "Urgent"]
    }
  }
}
</code></pre>

Один запрос может содержать сразу несколько вопросов разных типов. Именно это делает decision-модели удобными для триажа: одна операция, одно состояние, несколько независимых решений.

<h2>Python без дополнительных библиотек</h2>

Для запросов достаточно стандартного urllib, отдельный SDK не обязателен:

<pre><code>
import json
from urllib.request import Request, urlopen

OLLAMA_DECISION_URL = "http://localhost:11434/v1/systemone"

def ask_decision(state, questions, model="tev1:0.8b"):
    payload = {
        "model": model,
        "state": state,
        "questions": questions,
    }
    request = Request(
        OLLAMA_DECISION_URL,
        data=json.dumps(payload).encode(),
        headers={"Content-Type": "application/json"},
        method="POST",
    )
    with urlopen(request, timeout=3600) as response:
        return json.loads(response.read().decode())["answers"]
</code></pre>

Использование:

<pre><code>
answers = ask_decision(
    {"message": "Senior Swift developer, Berlin, remote friendly"},
    {
        "isJob": {
            "type": "noul",
            "instructions": "Does the message advertise a job posting that someone can apply to?"
        }
    },
)

probability = answers["isJob"]["noul"]
is_job = probability >= 0.5
</code></pre>

Если нужен официальный Python SDK, он называется typesafe-sdk. Для localhost его можно направить на Ollama переменными окружения TYPESAFE_BASE_URL, TYPESAFE_API_KEY и TYPESAFE_DEFAULT_MODEL. Но для простых задач хватает и прямого HTTP-запроса.

<h2>Как понять, что модель поддерживает decision</h2>

Decision-модели не умеют отвечать через /api/generate или /api/chat. Если отправить такой запрос, Ollama вернёт ошибку 400 с текстом вида:

<pre><code>
"tev1:0.8b" does not support generate
</code></pre>

Это важно, если у вас уже есть код, который работает с обычными моделями через /api/generate: при смене модели на decision-модель он перестанет работать. Правильнее заранее узнать возможности модели через /api/show и выбрать подходящий способ вызова:

<pre><code>
import json
from urllib.request import Request, urlopen

OLLAMA_SHOW_URL = "http://localhost:11434/api/show"

def supports_decision(model):
    request = Request(
        OLLAMA_SHOW_URL,
        data=json.dumps({"model": model}).encode(),
        headers={"Content-Type": "application/json"},
        method="POST",
    )
    try:
        with urlopen(request, timeout=30) as response:
            capabilities = json.loads(response.read().decode()).get("capabilities", [])
    except (OSError, TypeError, ValueError):
        return False
    return "decision" in capabilities
</code></pre>

У decision-моделей в capabilities будет только decision. У обычных моделей там будут completion, tools или другие возможности. Если Ollama недоступна, разумно считать модель обычной и использовать генеративный путь.

<h2>Как встроить в существующий код</h2>

Самый простой способ — не переписывать классификатор, а разделить его на две стратегии. Генеративная стратегия работает как раньше: собирает промпт, отправляет его в /api/generate и разбирает JSON. Decision-стратегия отправляет состояние и типизированный вопрос в /v1/systemone и сравнивает вероятность с порогом.

Выбор стратегии происходит в одном месте, при создании классификатора:

<pre><code>
def create_classifier(model):
    if supports_decision(model):
        return DecisionClassifier(model)
    return GenerativeClassifier(model)
</code></pre>

У такого подхода есть несколько преимуществ. Генеративные модели продолжают работать без изменений. Decision-модель можно включить сменой одной переменной окружения. А вся разница между двумя способами сосредоточена в двух небольших классах, а не размазана по приложению.

Для бинарной классификации decision-стратегия выглядит примерно так:

<pre><code>
async def classify(text):
    answers = await ask_decision(
        {"message": text},
        {
            "isJob": {
                "type": "noul",
                "instructions": instructions,
            }
        },
        model,
    )
    probability = answers["isJob"]["noul"]
    return probability >= 0.5, probability
</code></pre>

Обратите внимание, что decision-модель не возвращает объяснение. Если в вашем формате результата есть поле reason, его можно построить из вероятности: например, сохранить саму вероятность или строку вида "модель оценила сообщение в 0.935 как вакансию". Это честнее, чем выдумывать причину, которой модель не давала.

<h2>Инструкции должны быть вопросом</h2>

Это самый важный практический вывод. Decision-модели плохо понимают длинные промпты в стиле "ты классифицируешь сообщения, отвечай true, если..., иначе false". Им нужен короткий прямой вопрос.

На одном и том же сообщении про вакансию я получил такие вероятности:

<ul>
<li>Прямой вопрос "Is this message a job posting?" — 0.921.</li>
<li>Длинная инструкция с объяснением, что считать вакансией — 0.026.</li>
<li>Длинная инструкция с вопросом в конце — 0.391.</li>
</ul>

Разница почти в тридцать раз. Модель не ошибается в классификации, она просто не понимает, что от неё хотят, когда вопрос спрятан внутри абзаца. Поэтому для decision-моделей стоит держать отдельные короткие инструкции, а длинные промпты оставить генеративным моделям.

Удобно завести отдельную переменную окружения:

<pre><code>
OLLAMA_JOB_CLASSIFIER_DECISION_INSTRUCTIONS=Does the message advertise a job posting that someone can apply to?
</code></pre>

А обычный промпт использовать только для генеративного пути.

<h2>Порог и вероятности</h2>

Порог 0.5 подходит как значение по умолчанию, но его полезно вынести в конфигурацию. Для разных задач цена ложноположительного и ложноотрицательного ответа разная. Для модерации безопаснее поднять порог, для поиска вакансий — снизить, чтобы не пропустить полезные сообщения.

Полезно также логировать саму вероятность, а не только итоговый boolean. Когда классификатор ошибается, по логу видно, был ли это уверенный ответ или решение на границе. Для choice-вопросов стоит сохранять probabilities и confidence: они показывают, насколько модель колеблется между вариантами.

<h2>Производительность и память</h2>

Скорость сильно зависит от размера модели и железа. На CPU в моих тестах получились такие цифры:

<ul>
<li><b>tev1:0.8b</b> — доли секунды на решение, легко помещается в память.</li>
<li><b>tev1</b> — 4B, заметно медленнее, но всё ещё пригодна для интерактивных задач.</li>
<li><b>nimble</b> — 9B в Q8_0, около 10 ГБ в памяти. Первый запрос вместе с загрузкой модели занял около 137 секунд, последующие решения — от 12 до 32 секунд на CPU.</li>
</ul>

Nimble требует много оперативной памяти. На машине с 16 ГБ и Docker/WSL с лимитом около 8 ГБ модель не помещается: система начинает свопиться и контейнеры перестают отвечать. Помогло увеличение лимита WSL до 12 ГБ через файл .wslconfig:

<pre><code>
[wsl2]
memory=12GB
swap=8GB
</code></pre>

После изменения нужен wsl --shutdown и перезапуск Docker Desktop. Но даже с 12 ГБ запас остаётся небольшим: модель занимает около 10 ГБ, и на систему остаётся не так много.

По умолчанию Ollama выгружает модель после пяти минут простоя, освобождая память. Это удобно: nimble не держит 10 ГБ занятыми постоянно, но каждый новый запуск после паузы снова включает загрузку модели.

<h2>Когда использовать decision-модели</h2>

Decision-модели хорошо подходят для задач, где нужен быстрый и дешёвый ответ на чётко сформулированный вопрос:

<ul>
<li>Классификация сообщений, тикетов и заявок.</li>
<li>Маршрутизация по командам или исполнителям.</li>
<li>Модерация контента и проверка на безопасность.</li>
<li>Быстрые бинарные и многовариантные решения в игровых или интерактивных приложениях.</li>
</ul>

Они плохо подходят для задач, где нужен развёрнутый текст: объяснение, извлечение полей, суммаризация, генерация ответа. Для этого остаются обычные генеративные модели. Лучший результат получается при сочетании: decision-модель принимает решение, а генеративная модель объясняет его или извлекает данные.

<h2>Итог</h2>

Decision-модели в Ollama — это отдельный, более узкий инструмент, чем обычные LLM. Они не заменяют генеративные модели, но забирают у них рутинную часть работы: типизированные ответы, вероятности вместо парсинга текста и предсказуемый формат. Если у вас уже есть пайплайн классификации, переход сводится к проверке capabilities модели, отдельной стратегии вызова и коротким инструкциям-вопросам.
