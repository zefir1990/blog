Title: LiteLLM — единый шлюз к ста моделям
Slug: litellm-ai-gateway
Categories: notes
LiteLLM — открытый AI-шлюз, который даёт один интерфейс к сотне с лишним провайдеров больших языковых моделей. OpenAI, Anthropic, Gemini, Bedrock, Azure, DeepSeek, Mistral, Groq, Ollama, vLLM и десятки других сервисов вызываются в формате OpenAI, а не каждый по своим правилам. Проект развивает компания BerriAI, код распространяется под лицензией MIT, а на момент публикации у репозитория около 64 тысяч звёзд.

Проблема, которую решает LiteLLM, знакома каждому, кто писал что-то сложнее одного запроса к одной модели. У каждого провайдера свой SDK, свои имена переменных с ключом, своя структура запроса, свои коды ошибок и свои особенности потоковой передачи. Стоит добавить вторую модель для резерва или более дешёвую для рутины, и в коде начинается ветвление, а в конфигурации — зоопарк ключей. LiteLLM убирает это ветвление: приложение разговаривает с одним адресом, а переключение между провайдерами сводится к смене строки с именем модели.

Проект существует в двух видах, и это важно понимать сразу.

<ul>
<li><b>Python SDK.</b> Библиотека для приложений на Python. Один вызов <b>completion</b> вместо шести разных клиентов.</li>
<li><b>AI Gateway (Proxy Server).</b> Отдельный сервис, который поднимается рядом с приложением или на сервере и предоставляет HTTP API. К нему подключаются любые клиенты, умеющие работать с OpenAI, включая те, что написаны не на Python.</li>
</ul>

Второй вариант сейчас основной: по сути LiteLLM — это самостоятельный шлюз, у которого ядро написано на Rust, а Python SDK остаётся для встраивания в код.

<h2>Python SDK</h2>

Установка через uv:

<pre><code>
uv add litellm
</code></pre>

Дальше достаточно поменять импорт и имя модели. Ключи читаются из привычных переменных окружения провайдеров:

<pre><code>
from litellm import completion, completion_cost
import os

os.environ["OPENAI_API_KEY"] = "sk-..."
os.environ["ANTHROPIC_API_KEY"] = "sk-ant-..."

response = completion(
    model="openai/gpt-6.1-sol",
    messages=[{"role": "user", "content": "Привет"}],
)

print(response.choices[0].message.content)
print(completion_cost(completion_response=response))
</code></pre>

Модель задаётся строкой с префиксом провайдера. Чтобы перейти на другую, меняется только она:

<pre><code>
response = completion(
    model="anthropic/claude-sonnet-5",
    messages=[{"role": "user", "content": "Привет"}],
)

response = completion(
    model="deepseek/deepseek-chat",
    messages=[{"role": "user", "content": "Привет"}],
)
</code></pre>

Остальной код при этом не трогается: структура ответа та же, что у OpenAI. Для локальных моделей работает Ollama и любой OpenAI-совместимый сервер:

<pre><code>
response = completion(
    model="ollama/qwen3-coder",
    messages=[{"role": "user", "content": "Привет"}],
    api_base="http://localhost:11434",
)
</code></pre>

В SDK есть собственный роутер, который умеет держать несколько развёртываний одной модели, повторять запросы и уходить на резерв при ошибке:

<pre><code>
from litellm import Router

router = Router(
    model_list=[
        {
            "model_name": "main",
            "litellm_params": {
                "model": "openai/gpt-6.1-sol",
                "api_key": "os.environ/OPENAI_API_KEY",
            },
        },
        {
            "model_name": "backup",
            "litellm_params": {
                "model": "anthropic/claude-sonnet-5",
                "api_key": "os.environ/ANTHROPIC_API_KEY",
            },
        },
    ],
    fallbacks=[{"main": ["backup"]}],
    num_retries=2,
)

response = router.completion(
    model="main",
    messages=[{"role": "user", "content": "Привет"}],
)
</code></pre>

Для тестов предусмотрен режим заглушки: параметр <b>mock_response</b> возвращает заданный текст без обращения к сети, а флаг <b>litellm.drop_params</b> выкидывает параметры, которые конкретная модель не поддерживает.

<h2>Прокси-сервер</h2>

Шлюз ставится одной командой и запускается без базы данных:

<pre><code>
uv tool install 'litellm[proxy]'
litellm --model gpt-6.1-sol
</code></pre>

Сервер слушает порт 4000. Дальше подключается любой клиент OpenAI, достаточно поменять базовый адрес:

<pre><code>
curl http://localhost:4000/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "gpt-6.1-sol",
    "messages": [{"role": "user", "content": "Привет"}]
  }'
</code></pre>

Для нескольких моделей и правил маршрутизации нужен файл конфигурации. Вариант с тремя провайдерами и резервной цепочкой выглядит так:

<pre><code>
model_list:
  - model_name: fast
    litellm_params:
      model: openai/gpt-6.1-mini
      api_key: os.environ/OPENAI_API_KEY
      rpm: 500
  - model_name: smart
    litellm_params:
      model: anthropic/claude-sonnet-5
      api_key: os.environ/ANTHROPIC_API_KEY
  - model_name: local
    litellm_params:
      model: ollama/qwen3-coder
      api_base: http://localhost:11434

litellm_settings:
  drop_params: true
  num_retries: 3
  request_timeout: 60
  fallbacks:
    - smart: ["fast", "local"]
  context_window_fallbacks:
    - fast: ["smart"]

router_settings:
  routing_strategy: usage-based-routing
  allowed_fails: 3
  cooldown_time: 30

general_settings:
  master_key: os.environ/LITELLM_MASTER_KEY
</code></pre>

Запуск:

<pre><code>
export LITELLM_MASTER_KEY="sk-$(openssl rand -hex 24)"
litellm --config config.yaml
</code></pre>

Секция <b>model_list</b> задаёт то, что видит клиент, а <b>litellm_params.model</b> — то, куда запрос уходит на самом деле. Одно и то же имя <b>model_name</b> можно указать несколько раз с разными ключами или регионами, и LiteLLM начнёт балансировать между ними. При заданных <b>rpm</b> и <b>tpm</b> распределение становится взвешенным, а не равномерным.

<h2>Docker и панель управления</h2>

Полный вариант с PostgreSQL поднимается готовым compose-файлом. База включает виртуальные ключи, учёт расходов и панель:

<pre><code>
curl -sSLO https://github.com/BerriAI/litellm/raw/main/litellm/deploy/docker/docker-compose.quickstart.yml
printf 'LITELLM_MASTER_KEY=sk-%s\nLITELLM_SALT_KEY=sk-%s\n' "$(openssl rand -hex 32)" "$(openssl rand -hex 32)" > .env
docker compose -f docker-compose.quickstart.yml up -d
</code></pre>

После запуска панель открывается по адресу <b>http://localhost:4000/ui</b>. Логин <b>admin</b>, пароль — значение <b>LITELLM_MASTER_KEY</b> из <b>.env</b>. В интерфейсе добавляются модели с проверкой ключа, создаются виртуальные ключи и просматривается статистика.

Два ключа играют разные роли, и путать их нельзя:

<ul>
<li><b>LITELLM_MASTER_KEY</b> — административный ключ. Им подписываются запросы к Management API, он же служит паролем для входа в панель.</li>
<li><b>LITELLM_SALT_KEY</b> — ключ шифрования ключей провайдеров в базе. Он не ротируется на месте: после смены все сохранённые секреты станут нечитаемыми, пока их не введут заново.</li>
</ul>

Если база не нужна, тот же образ запускается с файлом конфигурации. В этом режиме запросы авторизуются мастер-ключом, а модели описаны только в YAML:

<pre><code>
docker run \
  -v "$PWD/config.yaml:/app/config.yaml:ro" \
  -e OPENAI_API_KEY \
  -e LITELLM_MASTER_KEY \
  -p 127.0.0.1:4000:4000 \
  docker.litellm.ai/berriai/litellm:latest \
  --config /app/config.yaml
</code></pre>

<h2>Виртуальные ключи, бюджеты и расходы</h2>

Главная причина, по которой шлюз ставят в команде, — не единый формат, а контроль доступа. Вместо ключа провайдера приложение получает виртуальный ключ со своими правами:

<ul>
<li>список разрешённых моделей;</li>
<li>лимит расходов на день, месяц или весь срок жизни ключа;</li>
<li>ограничения по числу запросов и токенов в минуту;</li>
<li>привязка к пользователю, команде или проекту;</li>
<li>срок действия и автоматический учёт потраченного.</li>
</ul>

Стоимость считается по таблице цен, которая лежит в репозитории и обновляется вместе с релизами. Поэтому расходы видны сразу после установки, без ручного заполнения прайс-листа. При превышении бюджета запросы начинают отклоняться с понятной ошибкой, а не молча уходить в минус.

Здесь есть важная оговорка: бюджеты и виртуальные ключи работают только при подключённой базе данных. Без неё <b>max_budget</b> не применяется — шлюз продолжает обслуживать запросы после достижения лимита и только пишет предупреждение в лог при старте. Запрос с виртуальным ключом в такой конфигурации вернёт ошибку <b>No connected db</b>, а мастер-ключ собственного бюджета не имеет.

<h2>Маршрутизация и отказоустойчивость</h2>

Помимо резервных моделей, LiteLLM умеет распределять нагрузку между несколькими развёртываниями. Доступные стратегии — простая случайная выборка, выбор наименее загруженного, маршрутизация по расходу токенов и по задержке. При нескольких экземплярах шлюза состояние балансировки и счётчики лимитов переносятся в Redis, иначе каждый экземпляр считает свою статистику отдельно:

<pre><code>
router_settings:
  redis_host: os.environ/REDIS_HOST
  redis_port: 6379
  redis_password: os.environ/REDIS_PASSWORD
</code></pre>

Кроме повторов и резервов, есть кэширование ответов, отдельная цепочка резервов при переполнении контекстного окна, период остывания для сбойного развёртывания и порог <b>allowed_fails</b>, который выводит его из ротации на время. Всё это настраивается в одном месте и не требует правок в приложении.

<h2>Наблюдаемость и интеграции</h2>

LiteLLM отдаёт логи и метрики во внешние системы через коллбэки: Langfuse, MLflow, Lunary, OpenTelemetry, Prometheus, Datadog и другие. Достаточно перечислить нужные в <b>success_callback</b> и <b>failure_callback</b>. Есть оповещения в Slack при приближении к бюджету, при зависших запросах и медленных ответах, гардрейлы для проверки входа и выхода модели, а также MCP-шлюз для подключения серверов инструментов к любому провайдеру.

Список эндпоинтов не ограничен чатом. Шлюз принимает запросы к <b>/chat/completions</b>, <b>/responses</b>, <b>/embeddings</b>, <b>/images</b>, <b>/audio</b>, <b>/batches</b>, <b>/rerank</b> и Anthropic-совместимому <b>/messages</b>. Поэтому к нему подключаются не только приложения, но и агентские инструменты, включая Claude Code, Codex и OpenCode: для них шлюз просто становится OpenAI- или Anthropic-совместимым адресом.

<h2>OpenCode через LiteLLM</h2>

Практическая связка выглядит так: LiteLLM держит ключи провайдеров, считает расходы и переключает модели, а OpenCode обращается к нему как к обычному OpenAI-совместимому сервису. В терминах OpenCode это собственный провайдер с базовым адресом шлюза.

Сначала в LiteLLM задаются имена моделей. Именно <b>model_name</b> из <b>config.yaml</b> увидит агент, а не строки вида <b>openai/gpt-6.1-sol</b>:

<pre><code>
model_list:
  - model_name: smart
    litellm_params:
      model: anthropic/claude-sonnet-5
      api_key: os.environ/ANTHROPIC_API_KEY
  - model_name: fast
    litellm_params:
      model: openai/gpt-6.1-mini
      api_key: os.environ/OPENAI_API_KEY
  - model_name: local
    litellm_params:
      model: ollama/qwen3-coder
      api_base: http://localhost:11434

litellm_settings:
  fallbacks:
    - smart: ["fast"]
</code></pre>

Для агента лучше выпустить отдельный виртуальный ключ на странице <b>Virtual Keys</b>, а не раздавать мастер-ключ. Тогда для OpenCode можно ограничить список моделей, поставить лимит расходов и отозвать доступ, не меняя ключи провайдеров. В режиме без базы данных остаётся только мастер-ключ.

Теперь провайдер описывается в глобальном конфиге OpenCode, файл <b>~/.config/opencode/opencode.jsonc</b>:

<pre><code>
{
  "$schema": "https://opencode.ai/config.json",
  "model": "litellm/smart",
  "providers": {
    "litellm": {
      "name": "LiteLLM",
      "env": ["LITELLM_API_KEY"],
      "package": "@opencode/ai/providers/openai-compatible",
      "settings": {
        "baseURL": "http://localhost:4000/v1"
      },
      "models": {
        "smart": { "name": "Smart" },
        "fast": { "name": "Fast" },
        "local": { "name": "Local" }
      }
    }
  }
}
</code></pre>

Ключ в файл не записывается: в поле <b>env</b> перечислены переменные, из которых OpenCode возьмёт учётные данные. Перед запуском агента переменная должна быть выставлена:

<pre><code>
export LITELLM_API_KEY=sk-your-virtual-key
opencode
</code></pre>

В Windows PowerShell вместо <b>export</b> используется <b>$env:LITELLM_API_KEY="sk-your-virtual-key"</b>.

После запуска модели видны в списке <b>/models</b>, а строкой <b>model</b> на верхнем уровне задаётся та, что выбирается по умолчанию. Конфигурация подхватывается без перезапуска: достаточно сохранить файл.

На что обратить внимание в этой связке:

<ul>
<li><b>Имена моделей.</b> Ключи в <b>models</b> должны совпадать с <b>model_name</b> из LiteLLM. Если указать <b>openai/gpt-6.1-sol</b>, OpenCode покажет провайдера, но запрос вернёт ошибку о недоступной модели.</li>
<li><b>Tool calling.</b> Агент постоянно вызывает инструменты, поэтому и основная, и резервная модели должны их поддерживать. Локальная модель без поддержки инструментов сорвёт работу, даже если отвечает на обычные вопросы.</li>
<li><b>Резервные цепочки.</b> OpenCode не знает, что запрос ушёл на другую модель, и это удобно: падение провайдера не ломает сессию. Но при переключении меняются качество и цена, а кэш промптов у нового провайдера будет холодным.</li>
<li><b>Контекст.</b> Лимиты контекста и стоимость можно указать в <b>models</b> вручную, тогда OpenCode будет показывать их в интерфейсе и предупреждать о переполнении. Это необязательно, но полезно, если модели в шлюзе не совпадают с каталогом models.dev.</li>
<li><b>Адрес.</b> <b>baseURL</b> должен заканчиваться на <b>/v1</b> и быть доступным из процесса OpenCode. Для шлюза в контейнере <b>localhost</b> указывает на сам контейнер, поэтому нужен адрес хоста.</li>
</ul>

Такой схемой удобно пользоваться и с другими агентами. Claude Code и Codex тоже умеют смотреть на OpenAI- или Anthropic-совместимый адрес, поэтому шлюз становится единой точкой, где видны расходы и ошибки всех инструментов сразу.

<h2>Что стоит учитывать</h2>

<ul>
<li><b>Это дополнительный слой.</b> Шлюз добавляет задержку к каждому запросу, пусть и небольшую: в документации заявлено около 8 мс на 95-м процентиле при тысяче запросов в секунду. Для локальных моделей и стриминга это не критично, но в нагруженной системе лишний сетевой переход всё равно стоит учитывать.</li>
<li><b>Простой режим ограничен.</b> Без базы нет ни ключей, ни бюджетов, ни учёта расходов. Для команды из нескольких человек база обязательна, а значит появляется Postgres, за которым тоже нужно следить.</li>
<li><b>Приоритет конфигурации.</b> Начиная с версии 1.103.0 ключ, объявленный в YAML, принадлежит файлу: правка через панель или API для него вернёт ошибку. Ключи, которых в файле нет, живут в базе. Это стоит учитывать при переходе со старых версий, где приоритет был обратным.</li>
<li><b>Часть возможностей платная.</b> Сам проект открытый и бесплатный, но SSO, аудит-логи, расширенное управление командами и часть гардрейлов относятся к Enterprise-лицензии.</li>
<li><b>Цены и модели меняются.</b> Таблица стоимости обновляется с релизами, но у новых моделей или региональных тарифов цифры могут отставать. Для точной сверки лучше держать собственные настройки цен.</li>
</ul>

LiteLLM хорошо подходит в двух случаях. Для небольшого проекта это способ не писать своё переключение между провайдерами и получить резерв почти бесплатно. Для команды это центральная точка доступа: ключи провайдеров лежат в одном месте, разработчики получают именные виртуальные ключи с лимитами, а расходы и ошибки видны в одном интерфейсе. Если приложению нужен только один провайдер и один ключ, шлюз, скорее всего, избыточен — хватит обычного SDK.
